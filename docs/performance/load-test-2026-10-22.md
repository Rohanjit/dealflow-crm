# Load test, 22 October 2026

Goal (Shobhit): push Dealflow until it fails, find where and why, then decide what to fix now.

## Set-up

- **Machine:** 2 CPUs, 7 GB memory (about a $24/month server). The load generator ran on the same
  machine, so real capacity is somewhat higher than measured.
- **Production settings:** gunicorn with 3 workers and a 300-second limit, `DJANGO_DEBUG` off, SQLite
  encrypted with SQLCipher, audit log on, two-step sign-in for every simulated banker.
- **Two firms**, made with `python manage.py seed_load` (`DEALFLOW_LOAD_TEST=1`):

| | Big firm (scale 1) | Extreme firm (scale 20) |
|---|---|---|
| Investors | 5,000 | 100,000 |
| Contacts | 20,000 | 400,000 |
| Companies | 2,500 | 50,000 |
| Outreach attempts | 4,000 | 80,000 |
| Deals (10% restricted), tracker entries | 400, 8,000 | 8,000, 160,000 |
| Log entries | 50,000 | 1,000,000 |
| Tasks, Vault documents | 5,000, 1,000 | 100,000, 20,000 |
| Bankers | 200 | 200 |
| Database size | 29 MB | 584 MB |

- **Tools** (in the repo): `seed_load` (the firm), `load_probe` (every screen's request once, with time,
  database queries and memory), `scripts/loadtest/locustfile.py` (many bankers at once: real sign-in,
  browsing, searching, editing and the bell polling every minute; `pip install locust`).

## Many bankers at once

Each simulated banker signs in, then every 3–10 seconds opens a list, a record, search, the home page or
insights, edits now and then, and polls the bell once a minute. That is far busier than a real person.

| Bankers active at once | Big firm: typical / slowest 5% | Extreme firm |
|---|---|---|
| 10 | 20 ms / 0.6–1.1 s | server frozen: a trivial health check takes over 10 s |
| 25 | 40 ms / 0.25 s | frozen |
| 50 | 35–110 ms / 0.3–1.0 s | frozen; most requests time out after 60 s |
| 100 | 1.5–2.5 s / 2.4–3.5 s | — |
| 200 | 4–7.6 s / 5–8.8 s, health check up to 10 s | — |

- **Extreme firm:** breaks at about **5 bankers**. A few bell polls and insights requests occupy all 3
  workers for 20–60 seconds, and every other request, even a 10 ms one, waits behind them.
- **Big firm:** comfortable up to about **50 busy bankers** (a firm of 150–300 people in real use),
  slow at 100, failing at 200.
- **Sign-in failed with "database is locked" (18 times, at 100–200 bankers):** SQLite allows one writer;
  a sign-in that read first and then wrote couldn't get the lock. Fix: WAL mode and immediate
  transactions (or Postgres).
- Sign-in itself costs about 0.25 s of CPU (Argon2, on purpose); 200 people signing in together wait up to
  12 s. Acceptable.

## Postgres, same extreme firm

Postgres 16 (512 MB shared buffers) on the same machine, extreme firm, one banker at a time:

| Request | SQLite (encrypted) | Postgres |
|---|---:|---:|
| Contacts list / search | 5,059 / 9,332 | 1,186 / 1,619 |
| Investor tracker list, tasks all, outreach list | 2,868 / 1,614 / 1,103 | 155 / 180 / 167 |
| Stuck filters (outreach / deals) | 10,487 / 7,135 | 1,327 / 994 |
| Bell: stuck and follow-ups (admin / member) | 24,762 / 21,437 | 2,754 / 9,082 |
| Global search | 10,312 | 2,799 |
| Investor matching | 26,736 | 28,929 |
| Insights | 35,212 | 22,682 |
| People you've emailed | 239,458 | 243,808 |
| Records, edits, notes, panels | 6–28 | 10–44 |

Postgres speeds up the parts the database does (sorting, filtering, counting) 3–20 times, but not the
parts done in Python (matching, insights, capture), and the bell is still far too slow. So moving to
Postgres helps big firms but is not the fix on its own: the code fixes below are needed either way.

## Failure points and scope

| # | Failure | Severity | Fix | Effort | Now? |
|---|---|---|---|---|---|
| 1 | Bell "stuck and follow-ups" recomputes stage history every poll | Critical (sinks the server) | Index log by module and kind; compute stage times once and reuse until the log changes; compute once per request, not 4× | ½–1 day | **Yes** |
| 2 | Backup holds the whole database in memory (4.2 GB; Docker allows 2 GB, so **no backups at this size**). Restore likely the same | Critical (data safety) | Stream the dump to a temporary file; later: native database dump | ½ day (stream) | **Yes** (stream); native later |
| 3 | List "Export" has no limit and builds the file in memory | Critical (one click can take the server down) | Same 50,000 limit as reports; write the file row by row; read linked values together | ½–1 day | **Yes** |
| 4 | Investor matching scores every investor | High | Narrow down in the database first (sector, currency, ticket), score at most a few thousand | ½–1 day | **Yes** |
| 5 | Lists sort on unindexed columns | High | Indexes on names, dates and stamps (one migration) | ½ day | **Yes** |
| 6 | People you've emailed / capture check rebuild indexes per row | High | Build once per request; match by indexed email and domain | ½ day | **Yes** |
| 7 | Insights page | High | Reuses #1; move per-entry loops into database aggregates | 1 day | **Yes** |
| 8 | SQLite "database is locked" under many writers | High (sign-in errors) | WAL mode + immediate transactions; recommend Postgres for large firms | 2 hours | **Yes** |
| 9 | Colleague's deals list: one query per restricted deal | Medium | One query for all placeholders | 2 hours | **Yes** |
| 10 | Going cold (admin) | Medium | Compare dates without converting each row; index Last contacted | 2 hours | **Yes** |
| 11 | Global search scans everything | High at extreme size, fine for a big firm | Short term: no exact counts, names first, cap per module. Long term: a real search index (SQLite FTS5 / Postgres trigram) | 1 day / 3–5 days | Short term **yes**; index later |
| 12 | Contacts "Find duplicates" (12 s, 1 GB) | Medium (rarely used) | Store normalised keys in columns and group in the database | 1 day | Later |
| 13 | Import of 10,000 rows uses 1 GB | Low | Read the file in pieces | 1 day | Later |
| 14 | Slow requests block fast ones (3 workers) | Medium after 1–11 | Threaded workers; heavy screens computed by the scheduler and cached | 1–2 days | After re-test |
| 15 | A killed backup blocks backups for an hour (stale lock) | Low | Use an operating-system lock that ends with the process | 1 hour | **Yes** |

"Now" items: about 4–5 days of work. Then the same tests run again to confirm.

## Fixes and results

| # | Fix | Before (extreme / big) | After (extreme / big) |
|---|---|---|---|
| 1 | Stage times learned by the scheduler and stored (`core.StageStats`), never read from the log by a screen; the bell filters "my records" in the database, builds names only for the 20 shown, checks meetings against tasks in one query; index on the log by module, kind and id | Bell 24,762 / 635 ms; member 21,437 / 942 ms; Stuck filters 10,487 and 7,135 ms; stage rules 8,240 ms | Bell 611 / 319 ms; member 598 / 280 ms; Stuck filters 519 and 116 ms; stage rules 5 ms |
| 2 | Backups written as a stream: records read 2,000 at a time (linked values per batch, not per record), compressed and encrypted as written; restores and restore tests read the encrypted file in place and load one record at a time; no readable copy on disk | Backup 642 s, 4.2 GB (over Docker's 2 GB: no backups possible); restore and restore test read the whole data file into memory | Backup 346 s, 212 MB; restore test 1,714 s, 68 MB (+116 MB for the checking process), all 1.9 million rows matched; restore RESTORE_RESULT |
